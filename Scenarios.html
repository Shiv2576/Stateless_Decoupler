STATELESS DECOUPLER

K3s WordPress High-Availability Architecture
PRODUCTION READY
Date: August 2026 | Version: 2.1.0 | Uptime: 99.9% | Lead: DevOps Team
Architecture Flow: Load Balancer -> WordPress Pods -> Redis -> MySQL -> MinIO
01. First-Time Visitor Journey

User visits: https://mycoolstore.com

DNS Resolution -> Load Balancer
  • Domain resolves to K3s cluster's load balancer
  • Load balancer checks pod CPU utilization
  • Pod 1: 30% CPU | Pod 2: 45% CPU
  • Request routed to Pod 1 (least busy)
Inside Pod 1 - Nginx Container
  • Nginx receives request and checks for static files
  • Identifies as PHP request for index.php
  • Forwards to PHP-FPM container within same pod
Inside Pod 1 - PHP-FPM Container
  • PHP-FPM starts executing WordPress code
  • Checks for session cookie - None (first-time visitor)
  • WordPress attempts to create new session
  • Session storage configured for Redis (not local)
  • PHP-FPM connects to Redis service
Redis stores: session_id = "abc123" data = { user_id: null, cart: [] }
Database Queries with Redis Cache
  • WordPress queries MySQL for homepage data
  • Query: SELECT * FROM wp_posts WHERE post_type='page' AND post_name='home'
  • Query: SELECT * FROM wp_posts WHERE post_type='product' LIMIT 12
  • Query: SELECT * FROM wp_term_relationships WHERE ...
Redis Object Cache
WordPress checks Redis for 'homepage_data' - Cache miss
Queries MySQL and stores results in Redis (TTL: 1 hour)
Media Files - S3 Offload
  • WordPress looks for: /wp-content/uploads/product.jpg
  • S3 offload plugin intercepts the request
  • Generates CDN URL: https://cdn.mystore.com/product.jpg
  • Nginx serves redirect to CDN or proxies to MinIO
Response
HTML generated -> Nginx adds headers -> Sent to browser
Browser renders page with images loading from CDN
Time to First Byte: 180ms
Key Insight
Session data lives independently of pods in Redis. Any pod can serve future requests for this user.
02. Add to Cart (AJAX Request)
AJAX Request
POST /?wc-ajax=add_to_cart Payload: { product_id: 42, quantity: 1 }
Load Balancer Decision
  • Pod 1: 60% CPU (serving homepage)
  • Pod 2: 40% CPU
  • Load balancer routes to Pod 2 (least busy)
Pod 2 Processes Request
  • PHP-FPM receives request and checks session
  • Browser sends: Cookie: wordpress_session=abc123
  • WordPress connects to Redis: "Give me session abc123"
  • Redis returns: { user_id: null, cart: [] }
  • WordPress updates cart: { product_id: 42, quantity: 1 }
  • Saves back to Redis with updated cart data
Session Data Lives Outside Pod 2
The session data is NOT stored in Pod 2's local storage
It's stored in Redis (a separate service)

This means:
- If Pod 2 crashes -> Session data is safe
- If Pod 2 scales up -> New pod can read same session
- If Pod 2 scales down -> Session data persists
Response
Pod 2 sends: "Cart updated successfully!"
Session cookie remains the same
User doesn't know which pod served the request
03. Pod Failure and Self-Healing
Pod 1 Crashes
  • User is checking out, filling in shipping details
  • Pod 1 is handling this request
  • Pod 1 crashes (OOM, network issue, code bug)
Kubernetes Detects Failure
  • Kubelet (agent on node) notices Pod 1 is not responding
  • Kubelet marks Pod 1 as unhealthy
  • Kubernetes creates a new Pod 1 (fresh container)
User is Still on the Site
  • User refreshes or continues
  • Load balancer routes to Pod 2 (still running)
Pod 2 Has All the Context
  • Pod 2 receives the request
  • Reads session cookie: wordpress_session=abc123
  • Connects to Redis: "Give me session abc123"
Redis returns: { user_id: 123, cart: [product_42: 1, product_17: 3], checkout_data: { shipping: "address", payment: "credit_card" } }
  • Pod 2 continues the checkout process seamlessly
  • User never knew Pod 1 died
New Pod 1 Starts Up
  • Kubernetes: "Pod 1 is now running"
  • Pod 1 starts fresh - no session data, no media files
  • When user routes to Pod 1, it connects to Redis for session data
  • Pod 1 works perfectly
Result
User never notices the failure. Zero downtime experience.
04. Auto-Scaling (Traffic Surge)
Traffic Spikes
  • 9:00 AM: 50 concurrent users
  • 9:05 AM: 500 concurrent users
  • 9:10 AM: 2,000 concurrent users
Horizontal Scaling Triggered
  • Kubernetes Metrics Server: CPU usage at 85% across pods
  • Horizontal Pod Autoscaler (HPA): "We have 2 pods, need more"
  • HPA: "Scale to 5 replicas"
  • Kubernetes creates 3 new WordPress pods
New Pods Join the Cluster
  • Pod 3 starts: Fresh WordPress container
  • Pod 3: "I don't have any files in /wp-content/uploads/"
  • Pod 3: "I don't have any session data locally"
But Pod 3 Connects To
- Redis for sessions and object cache
- MinIO for media files
- MySQL for database
  • Pod 3 is fully functional in seconds
Load Balancer Distributes Traffic
  • 5 pods now handle traffic
  • Pod 1: 20% of traffic
  • Pod 2: 20% of traffic
  • Pod 3: 20% of traffic
  • Pod 4: 20% of traffic
  • Pod 5: 20% of traffic
Session Stickiness - Comparison
Without stateless decoupling:
- Session stored in Pod 1's local storage
- User must ALWAYS hit Pod 1 (sticky sessions)
- If Pod 1 dies -> User loses session

With stateless decoupling:
- Session in Redis
- User can hit ANY pod
- If Pod 1 dies -> Other pod can continue
- Perfect for horizontal scaling
Result
5 pods serve traffic -> 200% capacity. Zero session loss.
05. Media Upload to S3
User Uploads Image in WordPress Admin
  • User: "I want to add this product image: product_photo.jpg"
  • User clicks upload
WordPress Receives the File
  • WordPress normally: "Save to /wp-content/uploads/2026/08/product_photo.jpg"
  • But configured S3 offload
  • WordPress: "Actually, save to S3-compatible storage"
MinIO (S3) Storage Process
  • WordPress connects to MinIO using AWS S3 API
  • MinIO credentials: admin / password123
  • WordPress: "Upload file to bucket 'wordpress' with key '2026/08/product_photo.jpg'"
  • MinIO: "File saved successfully"
Access via: http://minio:9000/wordpress/2026/08/product_photo.jpg
CDN URL Generation
  • WordPress stores: "Product image is at S3"
  • WordPress generates CDN URL
https://cdn.mystore.com/2026/08/product_photo.jpg
  • If no CDN, uses MinIO proxy URL
Pod Independence
  • The file is NOT in any pod's local storage
  • Pod 1, 2, 3, 4, 5 ALL can access it via:
  • - MinIO directly
  • - CDN URL (if configured)
Disaster Recovery
If we delete ALL pods and recreate them:
- Files are still in MinIO
- WordPress installs reconnect to MinIO
- All media is still available
Stateless Media
Files persist even if all pods are deleted. New pods access existing media immediately.
06. Cache Invalidation and Updates
Editor Updates a Product Description
  • User clicks "Update" on product page
  • WordPress runs:
UPDATE wp_posts SET post_content='new description' WHERE ID=42
Redis Cache Invalidation
  • WordPress: "I have product_42 cached in Redis"
  • WordPress: "Delete key 'product_42_data' from Redis"
  • Redis: "Key deleted"
  • WordPress: "Also delete 'homepage_data' because product changed"
  • Redis: "Deleted"
Next Visitor Sees Updated Content
  • New visitor requests homepage
  • WordPress checks Redis for 'homepage_data'
  • Redis: "Not found (cache miss)"
  • WordPress queries MySQL for fresh data
  • WordPress saves to Redis with TTL: 1 hour
  • New visitor sees updated content
Consistency
All pods query Redis -> All see fresh data. Cache is shared across all pods.
